# Future blog post: Meta WhatsApp onboarding, or How a 200 Became a Treasure Hunt

Working title: **How to Teach Meta's WhatsApp Cloud API to Say Hello Without Losing the Will to Live**

Tone: warm, funny, detailed, practical, and reassuring. Explain the confusion without mocking beginners. The central joke is that Meta asks us to prove a callback URL before it tells us where the callback URL lives, then gives several different kinds of tokens that all look like long strings of regret.

## The actual journey

1. Build and deploy a Cloudflare Worker endpoint at `/webhooks/whatsapp`.
2. Generate our own arbitrary webhook verify token. Meta does not provide this token.
3. Configure the Meta callback URL and verify token together.
4. Discover that the Meta dashboard's OAuth login callback does not work naturally from a temporary Docker container because Safari's `localhost` is not the container's `localhost`.
5. Use a narrowly scoped Cloudflare API token instead of trying to repair the container OAuth callback.
6. Create the remote D1 database and deploy the Worker.
7. Set production Wrangler secrets separately from local `.dev.vars`.
8. Find the Meta WhatsApp setup under the `Connect on WhatsApp` use case, `Step 1. Try it out`, rather than assuming there is an obvious standalone API Setup page.
9. Distinguish the Meta test/business number (`From`) from the real human recipient (`To`).
10. Discover that Meta's dashboard test button and the system-user API token are separate authentication paths.
11. Use Meta's webhook sample panel to prove that Meta can reach the Worker. The resulting synthetic sender is intentionally rejected by the application's approved-sender policy.
12. Query the test phone number directly through Graph API and find it in `PENDING` / `NOT_VERIFIED` state.
13. Register the test number once through the official `/PHONE_NUMBER_ID/register` endpoint with a six-digit PIN. Do not repeatedly retry because Meta limits registration attempts.
14. Confirm the phone status becomes `CONNECTED`.
15. Bypass the broken Meta dashboard send button and send the `hello_world` template directly using the system-user WhatsApp token.
16. Receive the message on the personal WhatsApp number and reply to trigger the real inbound webhook path.
17. Discover that two WhatsApp Business Accounts existed in Business Settings: a Meta test WABA and a separate production/Embedded WABA. IDs, phone numbers, subscriptions, and status checks are all account-specific.
18. Subscribe the production WABA explicitly to the app with `POST /WABA_ID/subscribed_apps`. Verifying the callback URL alone is not enough.
19. Query `GET /WABA_ID/phone_numbers?fields=id,display_phone_number,status,code_verification_status` rather than trusting the dashboard labels.
20. For the real production number, observe `PENDING` plus `VERIFIED`: ownership verification was complete, but Cloud API registration was not. Call `/PHONE_NUMBER_ID/register` once with a chosen six-digit PIN, then confirm `CONNECTED` and `VERIFIED`.
21. Update the deployed Worker secrets from the test phone/WABA IDs to the production phone/WABA IDs. The inbound handler did not filter by IDs, but the outbound client and window tracker absolutely use the configured sending phone ID.
22. Run `wrangler tail` while sending a real message. A synthetic Meta webhook produced a visible Worker request, while Meta's dashboard payload viewer could show a real event without that event appearing in the Worker tail.
23. Confirm the production flow: real WhatsApp message, Worker `message event`, D1 persistence, acknowledgement reply, and subsequent WhatsApp status webhooks.

## Token glossary for the post

- **Webhook verify token**: invented by the developer; used only for Meta's GET verification handshake.
- **Meta App Secret**: used to verify `X-Hub-Signature-256` on incoming webhook requests.
- **WhatsApp access token**: bearer token used to call the WhatsApp Graph API; use a system-user token for durable development.
- **Cloudflare API token**: unrelated token used by Wrangler to deploy Workers and manage D1.
- **Phone Number ID**: Meta's identifier for the business/test sending number.
- **WABA ID**: identifier for the WhatsApp Business Account.
- **Recipient number**: the human's personal WhatsApp number, not the Meta test/business number.
- **Temporary dashboard token**: generated by the Meta Quickstart/API Setup panel for its own test button; not the durable token used by the Worker.
- **System-user token**: generated from Business Settings after assigning the app and WABA; the token used for real Graph API calls.
- **Business verification**: different from phone-number ownership verification and Cloud API registration. It was not required for this low-volume proof of concept once the phone was `CONNECTED`.

## The working diagnostic commands

Sanitized examples only—tokens should be loaded from an ignored environment file or entered interactively, never pasted into a blog post:

```sh
# Check a WABA's app subscription
curl -sS "https://graph.facebook.com/v26.0/WABA_ID/subscribed_apps" \\
  -H "Authorization: Bearer $WHATSAPP_ACCESS_TOKEN"

# Check the phone number's status
curl -sS -G "https://graph.facebook.com/v26.0/PHONE_NUMBER_ID" \\
  --data-urlencode "fields=id,display_phone_number,status,code_verification_status" \\
  -H "Authorization: Bearer $WHATSAPP_ACCESS_TOKEN"

# Subscribe the WABA to the app
curl -sS -X POST "https://graph.facebook.com/v26.0/WABA_ID/subscribed_apps" \\
  -H "Authorization: Bearer $WHATSAPP_ACCESS_TOKEN"
```

Do not include real IDs, phone numbers, access tokens, or family messages in the published examples.

## Lessons worth preserving

- The successful webhook sample proves reachability, signature acceptance, parsing, and D1 adapter state—but does not prove a real WhatsApp conversation works.
- The dashboard's `Send to server` test and the dashboard's outbound `Send message` button are different tests with different semantics and token paths.
- A WABA subscription is separate from configuring the app's webhook field and verifying the callback URL.
- `Unsupported post request` can mean the object exists but is pending, inaccessible to the token, or not ready for that operation.
- Meta can display an inbound event in its dashboard while the event is not visibly delivered to the external endpoint; `wrangler tail` is the reliable check for Worker execution.
- When debugging, query the WABA and phone status directly before changing application code.
- Meta's UI may display an object ID before the Graph API considers it usable.
- Generated Meta test numbers are special; their profiles cannot be edited like real business numbers.
- Keep the Worker callback URL stable and use the deployed `workers.dev` URL for Meta, not a temporary tunnel.
- Never put tokens, real phone numbers, private family messages, or production data in screenshots, blog drafts, or Git.
- Rotate any token that appears in a screenshot.

## The eventual punchline

The final test succeeded only after we stopped asking the dashboard politely and called the Graph API directly—with the correct system-user token, the correct production WABA and phone-number IDs, an explicit WABA subscription, and a phone number that had finally been registered. The software was not broken; the onboarding maze was. And the humble `wrangler tail` turned out to be the courtroom stenographer.
